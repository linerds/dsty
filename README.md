# dsty

Лінтер оформлення звітів за ДСТУ 3008:2015 для документів Typst: командний рядок і LSP-сервер для редактора.

Статична перевірка розбирає вихідний код без компіляції (`typst-syntax`), тож працює за мілісекунди з будь-якою версією шаблону й Typst. Повна перевірка (`--full`) ще й компілює документ нативним `typst` проєкту і перевіряє те, що видно лише на сторінках: кегль, інтервали, відступи, номери сторінок, рисунків і формул, перенесені таблиці, виноски. Зауваження вказують на рядок коду, більшість статичних мають автоматичне виправлення.

## Встановлення

Готовий бінарник для Linux (x86_64, aarch64, статичний) і macOS (Intel, Apple Silicon) — в архіві на сторінці релізів: розпакуйте й покладіть `dsty` у теку з `PATH`.

```sh
cargo install --git https://github.com/linerds/dsty                       # Rust 1.92+
mise use -g 'github:linerds/dsty[prerelease=true,minimum_release_age=0]'  # архів з релізу
nix profile install github:linerds/dsty                                   # зібрати з коду
nix run github:linerds/dsty -- check src/main.typ                         # без встановлення
```

Для повної перевірки потрібен `typst` 0.15+ у `PATH` (старіші версії працюють через `typst query`, повільніше). Пакунки typst шукає як звичайно, тож `TYPST_PACKAGE_PATH` від mise чи direnv має бути в середовищі, з якого запущено dsty.

## Командний рядок

```sh
dsty check src/main.typ            # перевірити документ (з усіма #include)
dsty check works/pz1 works/lb2     # теки з src/main.typ чи main.typ
dsty check src/main.typ --fix      # виправити, що можна, і записати файли
dsty check src/main.typ --full     # разом з повною перевіркою
dsty check . --statistics          # наприкінці: скільки зауважень кожного правила
dsty check . --format github       # анотації GitHub Actions
dsty rules                         # перелік правил
dsty explain list-punct            # суть правила й текст пункту стандарту
```

Формати `--format`: `pretty` (як у typst: код з позначкою, вся позиція переліку чи наступна формула, довгі рядки перенесено по 80 знаків; типовий у терміналі), `text` (`файл:рядок:кол: [правило] …`, типовий у конвеєрі), `json`, `github`.

Код виходу: 0 — зауважень немає або лише підказки й рекомендації (`info`, `hint`), 1 — є зауваження, 2 — помилка (немає файлу, невідоме правило).

Корінь для шляхів `/…` визначається сам: тека main-файлу або найближча вище, у якій знаходяться всі імпорти `/…` (не вище теки з `typst.toml` чи `.git`). Задати явно: `--root`.

## Редактор

### Helix

`~/.config/helix/languages.toml` (або `.helix/languages.toml` проєкту):

```toml
[language-server.dsty]
command = "dsty"
args = ["lsp"]
config = { full = true }

[[language]]
name = "typst"
language-servers = ["tinymist", "dsty"]
```

`config` Helix передає як `initializationOptions` і, після `:config-reload`, як `workspace/didChangeConfiguration`.

### Neovim 0.11+

```lua
vim.lsp.config("dsty", {
  cmd = { "dsty", "lsp" },
  filetypes = { "typst" },
  root_markers = { ".dsty.toml", "typst.toml", ".git" },
  init_options = { full = true },
})
vim.lsp.enable("dsty")
```

### Що вміє сервер

- зауваження під час набору (типово через 150 мс після зміни) для main-документа й усіх файлів, які він підключає; відкритий файл, якого main не підключає, перевіряється окремо;
- main-документ: `main` з налаштувань, інакше `src/main.typ` чи `main.typ` робочої теки, інакше найближчий над відкритим файлом (не вище робочої теки й теки з `typst.toml`, `.git`, `.dsty.toml`), тож розділ роботи перевіряється разом з документом, навіть якщо редактор відкрив теку всього курсу;
- швидкі виправлення й «Виправити все у файлі» (також як `source.fixAll` при збереженні, навіть для одного зауваження);
- «Виправити все в документі» (`source.dsty.fixDocument`): main і всі підключені файли однією дією, як `check --fix`;
- підказка (hover) на зауваженні чи на назві правила в `dstu-ignore`: суть правила й текст пунктів ДСТУ 3008:2015;
- доповнення в коментарях: `// dstu-` -> вид коментаря, після `:` -> назви правил;
- повна перевірка при відкритті й збереженні (з `full = true`) або на вимогу: дія «dsty: повна перевірка документа зараз» чи команда `dsty.fullCheck`; хід видно через `$/progress`;
- рекомендації стандарту приходять як `information`, зайві `dstu-ignore` — як притінена підказка.

## Налаштування

`.dsty.toml` (чи `dsty.toml`) шукається від теки main-файлу вгору, тож один файл над теками робіт діє на весь курс. Його читають і `dsty check`, і сервер (перечитує після зміни). Відносні шляхи — від теки файлу.

```toml
main = "src/main.typ"        # main-файл для сервера (типово src/main.typ або main.typ)
root = "."                   # корінь для шляхів /…
full = true                  # повна перевірка
typst = "/шлях/до/typst"     # або назва з PATH (typst-0.15); типово typst з PATH
ignore = ["heading-single"]  # не перевіряти
enable = ["unit-space"]      # необов'язкові правила

[severity]                   # error, warning, info, hint або off
list-punct = "hint"
keywords-order = "warning"
```

Налаштування редактора мають ті самі ключі плюс `debounce` (мс) і `checkOnChange` (перевіряти під час набору, типово так). Вони діють поверх файлу: прості значення заміняють, переліки доповнюють. У командному рядку поверх файлу діють прапорці; `--config` задає інший файл, `--no-config` вимикає.

## Вимкнення правил у коді

```typst
- Велика літера; // dstu-ignore: list-case
// dstu-ignore-next-line: list-case, list-punct
- Ще одна
// dstu-ignore-file: heading-single
```

Коментар без переліку вимикає всі правила. Невідома назва правила (`ignore-unknown`) і назва, яка в рядку нічого не вимикає (`ignore-unused`), теж дають зауваження з виправленням.

## Повна перевірка

dsty подає `typst eval --in -` обгортку, яка підключає документ і додає невидимі проби (`src/full/probe.typ`): кольорові позначки виду тексту, `metadata` з ефективними стилями абзаців і заголовків, межі таблиць. Розкладку проби не змінюють (це перевіряє тест), у проєкт нічого не пишеться. Результат прив'язується до коду за мітками, текстом заголовків і назв, початком абзаців, тож під час набору зауваження не з'їжджають, а компіляція повторюється лише при збереженні. Межі: 60 с і 4 ГБ пам'яті на компіляцію.

Якщо документ не компілюється чи typst не знайдено, лишаються статичні зауваження, а причина — у журналі сервера (stderr у командному рядку).
